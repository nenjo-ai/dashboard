## Core Positioning

Nenjo is not just a place to run agents.

Nenjo is an **agent-first platform**: a system built so agents can do useful work inside the platform itself, not just call external tools from inside a hosted sandbox.

That means:

- agents can participate in platform operations, not just isolated task execution
- the platform is designed to be operable by agents
- teams keep control over runtime, routing, orchestration, security, and provider choice

The core distinction:

> Most products help you host agents.  
> Nenjo helps you build an agent-operable system.

## Short Version

Nenjo gives teams a provider-agnostic, agent-first runtime for building real agent products with control over orchestration, memory, routing, security, and platform behavior.

Nenji should support the landing page, not carry it.

Use Nenji to make the platform message more concrete:

- `Nenjo` is the platform
- `Nenji` is the example of an agent built for that platform model

- as a narrative bridge between platform architecture and user imagination

## Internal Competitive Notes

These points are for strategy and future copy decisions, not for direct homepage use.

### Against managed runtime products

Nenjo should emphasize:

- provider portability
- manifest-based configuration as code
- ownership of runtime and control plane
- multi-agent orchestration depth
- platform-level operability by agents
- product-grade multi-tenant architecture

### Against hosted template products

Nenjo should emphasize:

- not tied to one hosted runtime or one agent framework
- agent definitions that live in code and move across environments
- not limited to template-driven deployment
- stronger story for orchestration, routing, memory, and system design
- better fit for teams building a platform or product, not just deploying a hosted agent

### Honest concession

Do not pretend Nenjo wins on instant hosted convenience.

The fair concession is:

- hosted template products are usually better for time-to-first-agent
- managed runtimes are usually better for teams that do not want infrastructure

Then pivot:

`Nenjo is for teams who want more leverage, more control, and fewer long-term architectural constraints.`
