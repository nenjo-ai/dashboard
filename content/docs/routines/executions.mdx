Your routine is built—now make it run. Think of a routine as a recipe: the DAG structure is the recipe card, and an **execution** is the act of cooking it. Each time you run a routine, Nenjo creates a new execution context that tracks progress, accumulates results, and broadcasts events for monitoring.

## What happens when you run a routine

When a routine executes, the worker:

1. Creates a `RoutineContext` with project metadata, git context, and task data
2. Starts at the entry point step
3. Runs each step, storing results in the context
4. Evaluates edge conditions (`on_pass`, `on_fail`) to decide the next step
5. Continues until reaching a terminal step

## RoutineContext

The execution context flows through every step. Steps can read from it (to access task metadata or gate feedback) and the executor writes to it after each step completes.

### Core fields

| Field | Type | Description |
|---|---|---|
| `routine_id` | UUID | The routine being executed |
| `project_id` | UUID | The project this execution belongs to |
| `initial_input` | string | The input text that started the routine |
| `max_retries` | integer | Maximum retry attempts (from routine config) |
| `step_results` | map | Results keyed by step ID, accumulated during execution |
| `execution_run_id` | UUID? | The execution run record ID (null for chat routines) |
| `task_id` | UUID? | The task being processed (null for chat/cron routines) |
| `is_cron_trigger` | boolean | When true, agent steps use the role's `cron_task` template |

### Task metadata

| Field | Template variable | Description |
|---|---|---|
| `task_title` | `{{ task.title }}` | Task title |
| `task_description` | `{{ task.description }}` | Task description |
| `task_acceptance_criteria` | `{{ task.acceptance_criteria }}` | Acceptance criteria |
| `task_tags` | `{{ task.tags }}` | List of tags |
| `task_source` | `{{ task.source }}` | Who created/triggered: `"user"` or a role name |
| `task_status` | `{{ task.status }}` | Status: `open`, `ready`, `in_progress`, `done` |
| `task_priority` | `{{ task.priority }}` | Priority: `low`, `medium`, `high`, `critical` |
| `task_type` | `{{ task.type }}` | Type: `bug`, `feature`, `task` |
| `task_slug` | `{{ task.slug }}` | URL-safe identifier |
| `task_complexity` | `{{ task.complexity }}` | Estimated complexity score |

| `gate_feedback` | `{{ gate_feedback }}` | Output from the most recent failed gate/cron/lambda step |

## StepResult

Every step produces a `StepResult` stored in the context and used for edge evaluation.

| Field | Type | Description |
|---|---|---|
| `passed` | boolean | Whether the step succeeded |
| `output` | string | The step's output text |
| `data` | JSON | Structured data (optional) |
| `step_id` | UUID | ID of the step that produced this result |
| `step_name` | string | Name of the step |
| `input_tokens` | u64 | Total input tokens consumed (LLM steps) |
| `output_tokens` | u64 | Total output tokens consumed (LLM steps) |

## Data flow between steps

Data flows through the routine context:

1. **Initial input** — The `initial_input` string (task description or user message) is available to all steps.
2. **Step results** — Each step's `StepResult` is stored in `step_results` keyed by step ID.
3. **Gate feedback** — When a gate, cron, or lambda step fails, its output is stored as `gate_feedback`. The next agent step (via `on_fail` edge) can use this to understand what went wrong.
4. **Source tracking** — When a step fails, `task_source` is updated to the failing step's role name.

## Real-world example: error recovery flow

Here's how data flow enables error recovery:

```
Analyze (agent)
  --on_pass--> Implement (agent)
  --on_fail--> RequestClarification (agent)
```

When `Analyze` fails, its output (e.g., "Missing API endpoint documentation") becomes `gate_feedback`. The `RequestClarification` step receives this via `{{ gate_feedback }}` and can prompt the user for clarification:

```
The analysis failed because: {{ gate_feedback }}

What additional context can you provide?
```

## Monitoring executions

Subscribe to routine events via WebSocket for real-time tracking:

```javascript
const ws = new WebSocket('wss://your-instance.com/ws');

ws.onmessage = (event) => {
  const data = JSON.parse(event.data);
  
  switch (data.event_type) {
    case 'step_started':
      console.log(`▶ Starting: ${data.step_name}`);
      break;
    case 'step_completed':
      console.log(`✓ Completed: ${data.step_name} (${data.duration_ms}ms)`);
      break;
    case 'step_warning':
      console.log(`⚠ Step failed but recovery available: ${data.step_name}`);
      break;
    case 'step_failed':
      console.log(`✗ Step failed: ${data.step_name}`);
      break;
    case 'routine_completed':
      console.log(`✅ Routine completed successfully`);
      break;
    case 'routine_failed':
      console.log(`❌ Routine failed: ${data.error}`);
      break;
  }
};
```

### Event types

| Event type | Description |
|---|---|
| `phase_started` | A phase has started executing |
| `phase_completed` | A phase completed successfully |
| `phase_failed` | A phase failed (may retry) |
| `status_changed` | The task's status changed |
| `retry_scheduled` | A retry has been scheduled after a failure |
| `routine_completed` | The entire routine completed successfully |
| `routine_failed` | The routine failed permanently (max retries exceeded) |

### Step events

| Event | Description |
|---|---|
| `step_started` | Step began execution. Includes role info for frontend rendering. |
| `step_completed` | Step succeeded. Includes metrics: `execution_count`, `input_tokens`, `output_tokens`, `total_tokens`, `duration_ms`. |
| `step_warning` | Step failed but has an `on_fail` edge (recovery path available). |
| `step_failed` | Step failed with no recovery path. |


## Debugging: my routine hangs

If your routine seems stuck:

1. **Check WebSocket events** — Connect and watch for `step_started` without corresponding `step_completed`
2. **Check agent availability** — The assigned agent may be offline or busy
3. **Check for infinite loops** — Use [DAG validation](/docs/routines/dag-validation) to ensure no cycles
4. **Check cron step timeout** — A cron step with `timeout: "infinite"` will wait forever

## Debugging: my step keeps retrying

If a step retries indefinitely:

1. **Check max_retries** — The routine's `max_retries` setting limits attempts
2. **Check edge conditions** — If no `on_fail` edge exists, retries continue until max
3. **Check lambda/agent output** — Ensure the step outputs a clear signal (exit code 0 for lambdas, pass/fail for agents)
