Routines are **directed workflow graphs** that orchestrate agents, gates, councils, and terminal steps. They provide deterministic, auditable, and maintainable execution paths instead of relying on a single unstructured agent pass.

## What is a Routine?

A routine is a structured workflow defined by:

- **Steps** — Individual units of work (agent, gate, council, cron, terminal)
- **Edges** — Connections that define execution flow and dependencies
- **Trigger** — What causes the routine to start (`task` or `cron`)
- **Optional metadata** — Custom configuration per routine

Routines are **acyclic by default**, with the explicit exception of controlled review loops where a gate can send work back for refinement before final success or failure.

---

## Triggers

| Trigger | Description | Common Use Case |
|---------|-------------|----------------|
| `task` | Started when a project task is ready | Normal project work execution |
| `cron` | Started on a schedule | Periodic maintenance, monitoring |

**Task triggers** start when a task enters the ready state and is linked to a routine. **Cron triggers** start the routine on a defined schedule.

---

## Common Workflow Patterns

Routines are typically built using well-known patterns:

| Pattern | Description | Best Used When |
|---------|-------------|----------------|
| **Linear Pipeline** | Simple sequential execution of steps | Work naturally flows in a fixed order |
| **Gated Pipeline** | Sequential steps with validation gates | Quality or compliance must be checked |
| **Fan Out** | Parallel independent work followed by a join | Multiple independent analyses needed |
| **Review Pipeline** | Generation → Review → Approval/Rejection loop | Output quality requires review |

---

## Graph Structure

Routines form directed acyclic graphs (DAGs) where:

1. Execution flows from step to step along edges
2. Gates evaluate output and decide the next path
3. Councils run multi-agent collaboration when reached
4. The routine ends at a `terminal` (success) or `terminal_fail` (failure)

Every routine must have at least one reachable `terminal` or `terminal_fail` step.

**Key rules:**
- Circular dependencies between steps are rejected
- A gate can create a controlled loop back to an earlier step for rework
- Every step must have clear input/output contracts

---

## When to Use Routines

**Use a routine when:**
- Work requires multiple distinct steps
- Quality gates or validation are needed
- Multiple agents or perspectives are required
- The workflow has branching logic
- Auditability and observability matter

**Do not use a routine** when a single agent pass with relevant abilities would be simpler and clearer.

## Example: Gated Pipeline

```
┌─────────┐    ┌─────────┐    ┌─────────┐    ┌────────────┐
│ Generate │ → │  Gate   │ ──→│  Approve │ → │  terminal  │
│  Agent   │   │ Review  │    │  Agent   │    │  (success) │
└─────────┘    └─────────┘    └─────────┘
                    │
                    │ reject
                    ↓
              ┌────────────┐
              │ terminal_  │
              │   fail     │
              └────────────┘
```
