Your routine is built — now make it run. A **routine** is a recipe for getting work done: it specifies which steps to take and in what order.

Think of it like cooking:
- **Steps** are the recipe steps (chop onions, sauté garlic, add tomatoes)
- **Edges** are the "if this, then that" decisions (if onions are translucent, add garlic)
- The **DAG** (directed acyclic graph) is your flowchart — a visual map of the entire cooking process

## Why routines matter

Agents are powerful, but real work rarely fits in a single prompt. A routine lets you:

- **Chain agents together** — developer writes code → reviewer checks it → deployer ships it
- **Handle errors gracefully** — if review fails, loop back for fixes
- **Run on schedule** — cron routines check for new PRs every hour
- **Parallelize where possible** — split work across branches, then merge results

## A routine in action

Here's a simple code review flow:

```
Developer (agent) → Gate (review) → (on_pass) → Deploy (agent) → Terminal
                               → (on_fail) → Revise (agent) → Gate → ...
```

When the Developer finishes, the Gate evaluates the output:
- **Pass** → continue to Deploy
- **Fail** → route back to Revise for fixes

This is a DAG: steps are nodes, edges are arrows, and the graph has no cycles (you can't loop infinitely — each revision goes through a new gate).

## Real-world examples

### Simple review flow

A three-step routine for basic code review:

1. **Implement** — Agent writes code based on task
2. **Review** — Gate evaluates the code quality
3. **Terminal** — Done (or fail if review rejects)

```json
{
  "name": "Simple Review",
  "trigger": "task.ready",
  "steps": [
    { "name": "Implement", "step_type": "agent", "role_id": "developer-role-uuid" },
    { "name": "Review", "step_type": "gate", "role_id": "reviewer-role-uuid" },
    { "name": "Done", "step_type": "terminal" }
  ],
  "edges": [
    { "source_step_id": "implement-uuid", "target_step_id": "review-uuid", "condition": "always" },
    { "source_step_id": "review-uuid", "target_step_id": "done-uuid", "condition": "on_pass" }
  ]
}
```

### Parallel research team

Two agents research different topics simultaneously, then a third agent synthesizes:

```
Researcher A ──┐
               ├─→ Synthesize ──→ Terminal
Researcher B ──┘
```

```json
{
  "name": "Research Synthesize",
  "trigger": "task.ready",
  "steps": [
    { "name": "Research A", "step_type": "agent", "role_id": "researcher-role-uuid" },
    { "name": "Research B", "step_type": "agent", "role_id": "researcher-role-uuid" },
    { "name": "Synthesize", "step_type": "agent", "role_id": "writer-role-uuid" },
    { "name": "Done", "step_type": "terminal" }
  ],
  "edges": [
    { "source_step_id": "research-a-uuid", "target_step_id": "synthesize-uuid", "condition": "always" },
    { "source_step_id": "research-b-uuid", "target_step_id": "synthesize-uuid", "condition": "always" },
    { "source_step_id": "synthesize-uuid", "target_step_id": "done-uuid", "condition": "always" }
  ]
}
```

> **Note:** The executor follows edges sequentially. Both `always` edges from Research A and B will trigger, but only the first matching edge is followed at each step. For true parallel execution, use separate execution runs or a council.

## Core concepts

A routine has three primitives:

| Primitive | Analogy | Description |
|---|---|---|
| **Steps** | Recipe steps | Units of work — run an agent, evaluate a gate, execute a script |
| **Edges** | Decision arrows | Directed connections between steps — "if this passes, go there" |
| **Conditions** | If/then rules | Rules on edges that determine which path to follow |

### Entry and terminal points

Every routine needs:
- **One entry point** — a step with no incoming edges (where execution starts)
- **At least one terminal step** — where execution ends (either success or failure)

## Trigger types

Routines activate in two ways:

| Trigger | When it runs | Use case |
|---|---|---|
| `task.ready` | A task becomes ready | Most agent workflows |
| `cron` | On a schedule | Polling, periodic checks |

See [Cron and scheduling](/docs/routines/cron-and-scheduling) for cron details.

## What makes a routine invalid?

The validator catches common mistakes before you save:

| Error | What it means |
|---|---|
| "Routine must contain at least one step" | Add steps to your routine |
| "Must have exactly one entry point" | Ensure one step has no incoming edges |
| "Must have at least one terminal step" | Add a terminal or terminal_fail step |
| "Step not reachable from entry" | All steps must connect to the flow |
| "Contains a cycle" | No looping — use edges with conditions instead |
| "Agent step must have agent_id or role_id" | Assign an agent or role to agent steps |

See [DAG validation](/docs/routines/dag-validation) for the full ruleset.

## API quick reference

```bash
# Create a routine
curl -X POST https://your-instance.com/api/v1/routines \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Code Review",
    "trigger": "task.ready",
    "max_retries": 3
  }'

# Add a step
curl -X POST https://your-instance.com/api/v1/routines/$ID/steps \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Developer",
    "step_type": "agent",
    "role_id": "role-uuid"
  }'

# Connect steps with an edge
curl -X POST https://your-instance.com/api/v1/routines/$ID/edges \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "source_step_id": "step-a-uuid",
    "target_step_id": "step-b-uuid",
    "condition": "on_pass"
  }'
```
