---
title: Edges and conditions
description: How edge conditions control routine flow based on step results.
---

Edges are the decision arrows in your routine flowchart. They connect steps and determine which path to take next.

Think of edges as the "if this, then that" logic:
- "If the code compiles, run tests"
- "If tests pass, deploy"
- "If review fails, go back for fixes"

## Edge conditions

Each edge has a condition that tells the executor when to follow it:

| Condition | Follows when | Use case |
|---|---|---|
| `always` | Every time | Linear flow, parallel branches |
| `on_pass` | Step returned `passed: true` | Success path |
| `on_fail` | Step returned `passed: false` | Error handling, retry |
| `on_review_pass` | Step passed in review context | Review workflows |
| `on_review_fail` | Step failed in review context | Review correction |

### How conditions work

When a step finishes, the executor looks at its outgoing edges:

```
1. Get all edges leaving the current step
2. Find the first edge whose condition matches the result
3. Follow that edge to the next step
4. If no edge matches, execution ends
```

```json
{
  "source_step_id": "developer-uuid",
  "target_step_id": "reviewer-uuid",
  "condition": "on_pass"
}
```

## Common flow patterns

### Linear flow (always)

The simplest pattern — steps execute one after another:

```
Step A --always--> Step B --always--> Terminal
```

```json
{
  "edges": [
    { "source_step_id": "a", "target_step_id": "b", "condition": "always" },
    { "source_step_id": "b", "target_step_id": "terminal", "condition": "always" }
  ]
}
```

### Pass/fail branching

Route to different steps based on results:

```
Developer --on_pass--> Reviewer --on_pass--> Deploy --> Terminal
           --on_fail--> Fix --> Reviewer
```

```json
{
  "edges": [
    { "source_step_id": "developer", "target_step_id": "reviewer", "condition": "on_pass" },
    { "source_step_id": "developer", "target_step_id": "fix", "condition": "on_fail" },
    { "source_step_id": "fix", "target_step_id": "reviewer", "condition": "always" }
  ]
}
```

### Gate with review loop

A classic pattern: agent does work → gate reviews → if fail, agent fixes → repeat:

```
Implement --> Gate --on_pass--> Deploy --> Terminal
            |
            +--on_fail--> Fix --> Gate
```

The gate feedback tells the fix agent what went wrong.

### Diamond (fan-out)

Split work across multiple paths that converge:

```
Start --always--> Left --> Merge --> Terminal
     --always--> Right -/
```

```json
{
  "edges": [
    { "source_step_id": "start", "target_step_id": "left", "condition": "always" },
    { "source_step_id": "start", "target_step_id": "right", "condition": "always" },
    { "source_step_id": "left", "target_step_id": "merge", "condition": "always" },
    { "source_step_id": "right", "target_step_id": "merge", "condition": "always" }
  ]
}
```

> **Note:** The executor follows edges sequentially. Both `always` edges from Start will match, but only the first is followed. For true parallel execution, use separate execution runs or a council.

## Gate feedback flow

When a gate (or cron/lambda) fails, its output becomes `gate_feedback` in the routine context. The next agent step receives this feedback automatically.

This enables the review-fix-review loop without creating actual cycles:

```
Developer → Gate (fail) → Fix → Gate (pass) → Done
```

The feedback includes what the gate rejected, so the fix agent knows exactly what to address.

## Creating edges via API

```bash
# Create an edge with on_pass condition
curl -X POST https://your-instance.com/api/v1/routines/$ID/edges \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "source_step_id": "step-a-uuid",
    "target_step_id": "step-b-uuid",
    "condition": "on_pass"
  }'

# Create a fallback edge for failures
curl -X POST https://your-instance.com/api/v1/routines/$ID/edges \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "source_step_id": "step-a-uuid",
    "target_step_id": "fallback-uuid",
    "condition": "on_fail"
  }'
```

## Validation rules for edges

| Rule | Error | Fix |
|---|---|---|
| No self-loops | "Source and target must be different" | Connect to a different step |
| Both steps must exist | "Step not found" | Check step IDs |
| Steps must be in same routine | "Step not in routine" | Verify routine_id matches |

## What happens when no edge matches?

If a step completes but no outgoing edge matches the condition, execution ends:

- If the final step passed → routine succeeds
- If the final step failed → routine fails

This is why every meaningful step needs at least one outgoing edge (unless it's a terminal).
