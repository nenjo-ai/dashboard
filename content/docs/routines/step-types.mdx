Each step in a routine has a specific type that defines its behavior. This guide covers all available step types and when to use each.

## Step Type Overview

| Step Type | Description | Typical Use |
|----------|-------------|------------|
| `agent` | Executes a single agent with full task or context | Core work |
| `gate` | Evaluates evidence and branches (pass/fail) | Quality control, validation |
| `council` | Runs a structured multi-agent collaboration | Review, synthesis |
| `cron` | Internal scheduled step (rare) | Recurring sub-work |
| `terminal` | Successful end of the routine | Success path |
| `terminal_fail` | Explicit failure path | Error handling |

---

## Agent Steps

Agent steps execute a single agent with full task or context. This is the most common step type for core work.

**Behavior:**
- The assigned agent receives the task and current context
- The agent executes and returns a verdict (pass/fail)
- If the agent fails, the **entire routine fails** immediately

**Important:** Agent step failure causes immediate routine failure. There is no `on_fail` edge for agent steps.

```json
{
  "type": "agent",
  "agent_id": "writer-001",
  "on_complete": "gate-review"
}
```

---

## Gate Steps

Gate steps evaluate evidence and decide the next path based on pass/fail or approve/reject decisions.

**Behavior:**
- The gate agent evaluates the input against criteria
- Returns a pass/fail verdict with reasoning
- Execution follows the explicitly defined `on_pass` or `on_fail` edge
- Allows for graceful degradation, retry logic, or routing to failure paths

```json
{
  "type": "gate",
  "agent_id": "reviewer-001",
  "on_pass": "terminal",
  "on_fail": "agent-revise"
}
```

**Gate failure semantics differ from agent steps** — when a gate returns failure, execution routes to the `on_fail` edge rather than failing the entire routine.

### When to Use Gates

- **Quality control** — Verify output meets acceptance criteria
- **Validation** — Check compliance or security requirements
- **Approval workflows** — Require human or agent sign-off
- **Retry loops** — Send work back for revision before final success

---

## Council Steps

Council steps run a structured multi-agent collaboration as a single step. The council itself contains the leader and member agents.

**Behavior:**
- The council leader coordinates the collaboration
- Work is distributed to members based on the delegation strategy
- The leader synthesizes the final output
- Returns a single pass/fail verdict for the routine

```json
{
  "type": "council",
  "council_id": "code-review-council",
  "on_complete": "terminal",
  "on_error": "terminal_fail"
}
```

For details on council design, see [Councils](/docs/agents/councils).

---

## Cron Steps

Cron steps are internal scheduled steps used for recurring sub-work within a routine. They are rarely used and typically handled by the trigger instead.

**Behavior:**
- Runs on an internal schedule independent of the routine trigger
- Useful for periodic sub-tasks like status checks or cleanup

```json
{
  "type": "cron",
  "schedule": "0 * * * *",
  "on_complete": "terminal"
}
```

Most scheduling use cases should use the routine trigger (`cron`) rather than cron steps.

---

## Terminal Steps

Terminal steps mark the successful end of a routine.

**Behavior:**
- The routine completes successfully
- All output is captured and returned
- No further steps are executed

```json
{
  "type": "terminal",
  "label": "success"
}
```

Every routine must have at least one reachable `terminal` step.

---

## Terminal Fail Steps

Terminal fail steps mark an explicit failure path.

**Behavior:**
- The routine ends in a failure state
- The failure reason is captured
- Appropriate error handling can be triggered

```json
{
  "type": "terminal_fail",
  "label": "validation-failed"
}
```

**Best practice:** Define both success and failure terminal paths to ensure complete error handling.

---

## Failure & Verdict Handling

Every **agent step** and **gate step** is automatically exposed to a `pass_verdict` tool. This tool allows the agent to explicitly return a structured pass/fail verdict along with a reason.

**Key distinction:**
| Step Type | Failure Behavior |
|----------|------------------|
| `agent` | Entire routine fails immediately |
| `gate` | Routes to `on_fail` edge |

This distinction ensures critical work steps are atomic (failure = routine failure), while gates implement sophisticated error handling.
