title: Step types
description: Reference for all routine step types — Agent, Council, Gate, Cron, Lambda, Terminal, and TerminalFail.
---

Steps are the building blocks of your routine. Each step type does something different — think of them as different tools in your workshop:

- **Agent** = your worker who uses an LLM
- **Gate** = your quality checker
- **Lambda** = your automation script
- **Council** = your team meeting
- **Terminal** = the exit door

## Agent — Run an LLM task

The most common step. An agent uses an LLM to accomplish a work item.

### When to use

- Writing code, drafting documents, analyzing data
- Any task that benefits from LLM reasoning

### How it works

1. The agent receives the routine context (task details, git info, previous outputs)
2. The LLM generates a response
3. The step returns `passed: true` (or `false` if it fails)

### Agent resolution order

The system figures out which agent to run:

1. **`role_id`** on the step → looks up the role's assigned agent
2. **`agent_id`** on the step → uses that agent directly
3. **Fallback** → uses the first available agent

```json
{
  "name": "Write Code",
  "step_type": "agent",
  "role_id": "developer-role-uuid"
}
```

### Config options

| Field | Type | Description |
|---|---|---|
| `role_id` | UUID | Alternative to top-level role_id |
| `metadata` | JSON | Extra context injected as `{{ step.metadata }}` |

> **Tip:** For cron-triggered routines, agents use the role's `cron_task` template instead of `task_task`.

## Gate — Quality check

A gate evaluates the previous step's output using an LLM. It's your reviewer.

### When to use

- After an agent completes work
- To decide whether to continue or retry

### How it works

1. Gate receives the previous step's output
2. An LLM evaluates it against criteria
3. Returns `passed: true` or `false`

```json
{
  "name": "Review Code",
  "step_type": "gate",
  "role_id": "reviewer-role-uuid",
  "config": {
    "criteria": "Code compiles, has tests, follows style guide"
  }
}
```

### Config options

| Field | Type | Default | Description |
|---|---|---|---|
| `criteria` | string | "Evaluate whether the output is correct and complete." | What to check for |
| `metadata` | JSON | — | Extra context |

### Gate feedback

When a gate fails, its output becomes `gate_feedback` in the context. The next agent (via `on_fail` edge) can read this feedback to understand what needs fixing.

## Lambda — Run a script

A deterministic script with no LLM. Use for automation, tests, or API calls.

### When to use

- Running tests or linters
- Checking git status
- Calling external APIs
- Any deterministic task

### How it works

1. The script runs with routine context as environment variables
2. Exit code determines pass/fail (0 = pass, non-zero = fail)
3. stdout becomes the step's output

```json
{
  "name": "Run Tests",
  "step_type": "lambda",
  "lambda_id": "lambda-uuid",
  "config": {
    "timeout": "5m"
  }
}
```

### Config options

| Field | Type | Default | Description |
|---|---|---|---|
| `lambda_id` | UUID | — | Alternative to top-level lambda_id |
| `interpreter_override` | string | — | Force interpreter: `bash`, `python3`, `node` |
| `timeout` | string | `"5m"` | Max execution time |

See [Lambdas](/docs/routines/lambdas) for writing lambda scripts.

## Council — Multi-agent team

A council runs multiple roles in conversation. It's a team meeting.

### When to use

- Complex decisions requiring multiple perspectives
- Code review with multiple reviewers
- Brainstorming sessions

### How it works

1. Roles collaborate through structured conversation
2. The council returns a single unified result
3. `passed` reflects whether the council reached consensus

```json
{
  "name": "Architecture Review",
  "step_type": "council",
  "council_id": "council-uuid"
}
```

> **Note:** Councils require `council_id`. The council configuration (roles, orchestration) is defined separately.

## Cron — Scheduled polling

A step that repeats until it signals completion. Like an alarm that keeps ringing until you handle it.

### When to use

- Checking for new PRs every hour
- Polling an external API
- Waiting for a deployment to finish

### How it works

1. Runs the specified function (agent, lambda, or council)
2. Checks the output for status signal
3. Repeats on interval until pass, fail, or timeout

### Signaling

The function signals status via JSON output:

```json
{"cron_status": "pass", "reason": "PR merged"}
```

| Status | Meaning | Next step |
|---|---|---|
| `pass` | Work done successfully | Take `on_pass` edge |
| `fail` | Work done but failed | Take `on_fail` edge |
| `wait` | Not done yet | Sleep, then run again |
| `abort` | Unrecoverable error | Stop routine immediately |

```json
{
  "name": "Check PRs",
  "step_type": "cron",
  "role_id": "pr-checker-role-uuid",
  "config": {
    "interval": "30s",
    "timeout": "1h"
  }
}
```

### Config options

| Field | Type | Default | Description |
|---|---|---|---|
| `interval` | string | `"60s"` | How often to poll |
| `timeout` | string | `"24h"` | Max time before abort |
| `role_id` | UUID | — | Agent to run each cycle |
| `lambda_id` | UUID | — | Lambda to run each cycle |

Duration format: `30s`, `5m`, `1h`, `2d`.

See [Cron and scheduling](/docs/routines/cron-and-scheduling) for more.

## Terminal — Success end

Marks the routine as complete. The exit door for success.

### When to use

- End of any successful flow
- Required for every routine

### How it works

- Returns `passed: true` with the final output
- Must have no outgoing edges

```json
{
  "name": "Done",
  "step_type": "terminal"
}
```

## TerminalFail — Failure end

Marks the routine as failed. The exit door for errors.

### When to use

- Explicit failure path (e.g., after exhausting retries)
- When a particular outcome is a failure

### How it works

- Always returns `passed: false`
- Stores the failure reason as output

```json
{
  "name": "Rejected",
  "step_type": "terminal_fail",
  "config": {
    "failure_reason": "Code review rejected"
  }
}
```

### Config options

| Field | Type | Default | Description |
|---|---|---|---|
| `failure_reason` | string | "Routine terminated with failure" | Why it failed |

## Quick reference

| Step type | LLM? | Required field | Use case |
|---|---|---|---|
| `agent` | Yes | `agent_id` or `role_id` | Do work with an LLM |
| `gate` | Yes | `agent_id` or `role_id` (or fallback) | Evaluate quality |
| `lambda` | No | `lambda_id` | Run a script |
| `council` | Yes | `council_id` | Multi-agent discussion |
| `cron` | Depends | `role_id`, `lambda_id`, or `council_id` | Repeat until done |
| `terminal` | No | — | End successfully |
| `terminal_fail` | No | — | End with failure |
