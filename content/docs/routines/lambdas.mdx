title: Lambdas

Lambdas are **deterministic scripts** that run without an LLM. Use them for tasks like:

- Running tests or linters
- Checking git status
- Calling external APIs
- Performing file operations
- Polling for external conditions (in cron steps)

Think of lambdas as the **utility functions** of your routine—they do specific, repeatable tasks reliably.

## Creating a lambda

### Via API

```bash
curl -X POST \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Run Tests",
    "description": "Execute the project test suite",
    "path": "scripts/run-tests.sh",
    "body": "#!/bin/bash\nset -e\nnpm test",
    "interpreter": "bash"
  }' \
  https://your-instance.com/api/v1/lambdas
```

### Data model

| Field | Type | Description |
|---|---|---|
| `id` | UUID | Unique identifier |
| `name` | string | Human-readable name |
| `description` | string? | Optional description |
| `path` | string | Relative path within `~/.nenjo/lambdas/` |
| `body` | string | The script source code |
| `interpreter` | string | How to execute: `auto`, `bash`, `sh`, `python3`, or `node` |

### Interpreters

| Value | Description |
|---|---|
| `auto` | Execute directly (must have a shebang and be executable) |
| `bash` | Run with `/bin/bash` |
| `sh` | Run with `/bin/sh` |
| `python3` | Run with `python3` |
| `node` | Run with `node` |

## Using lambdas in routines

### Lambda steps

A lambda step runs once and determines the next step based on exit code:

```json
{
  "name": "Run Tests",
  "step_type": "lambda",
  "lambda_id": "LAMBDA_UUID",
  "config": {
    "timeout": "10m"
  }
}
```

- Exit code `0` → takes `on_pass` edge
- Non-zero exit → takes `on_fail` edge

### Cron steps (polling)

A cron step runs repeatedly until a condition is met:

```json
{
  "name": "Wait for Deployment",
  "step_type": "cron",
  "lambda_id": "CHECK_DEPLOY_LAMBDA",
  "config": {
    "interval": "30s",
    "timeout": "1h"
  }
}
```

The lambda signals completion via JSON output (see [Cron and Scheduling](/docs/routines/cron-and-scheduling)).

## Environment variables

Lambdas receive context via environment variables:

| Variable | Description |
|---|---|
| `NENJO_ROUTINE_ID` | Routine ID |
| `NENJO_STEP_ID` | Current step ID |
| `NENJO_STEP_NAME` | Current step name |
| `NENJO_PROJECT_ID` | Project ID |
| `NENJO_EXECUTION_RUN_ID` | Execution run ID |
| `NENJO_TICKET_ID` | Task ID |
| `NENJO_TICKET_TITLE` | Task title |
| `NENJO_TICKET_SLUG` | URL-safe task identifier |
| `NENJO_GIT_BRANCH` | Current working branch |
| `NENJO_GIT_WORK_DIR` | Worktree directory path |
| `NENJO_GIT_TARGET_BRANCH` | Target branch for merges/PRs |
| `NENJO_GIT_REPO_URL` | Remote repository URL |
| `NENJO_GIT_COMMON_DIR` | Main `.git/` directory path |
| `NENJO_CONTEXT_FILE` | Path to JSON file with full context |

### Context file

For complex data, read from `NENJO_CONTEXT_FILE`:

```python
import json
import os

with open(os.environ['NENJO_CONTEXT_FILE']) as f:
    context = json.load(f)

pr_number = context.get('pr_number')
```

## Lambda patterns with code examples

### Pattern 1: Git status check

Fail if there are uncommitted changes:

```bash
#!/bin/bash
# Lambda: check-git-status.sh

cd "$NENJO_GIT_WORK_DIR" || exit 1

if [ -n "$(git status --porcelain)" ]; then
  echo "Uncommitted changes detected:"
  git status --short
  exit 1
fi

echo "Working directory is clean"
exit 0
```

### Pattern 2: Run test suite

```bash
#!/bin/bash
# Lambda: run-tests.sh

cd "$NENJO_GIT_WORK_DIR" || exit 1

echo "Running test suite..."
npm test -- --ci

if [ $? -eq 0 ]; then
  echo "All tests passed"
  exit 0
else
  echo "Tests failed"
  exit 1
fi
```

### Pattern 3: PR merge check (cron lambda)

```bash
#!/bin/bash
# Lambda: check-pr-merged.sh
# For use in cron steps - polls until PR is merged

cd "$NENJO_GIT_WORK_DIR" || exit 1

# Read PR number from context file
PR_NUMBER=$(cat "$NENJO_CONTEXT_FILE" | python3 -c "import sys,json; print(json.load(sys.stdin).get('pr_number',''))")

if [ -z "$PR_NUMBER" ]; then
  echo '{"cron_status": "abort", "reason": "No PR number in context"}'
  exit 0
fi

STATE=$(gh pr view "$PR_NUMBER" --json state -q '.state' 2>/dev/null)

case "$STATE" in
  MERGED)
    echo "{\"cron_status\": \"pass\", \"reason\": \"PR #$PR_NUMBER merged\"}"
    ;;
  CLOSED)
    echo "{\"cron_status\": \"fail\", \"reason\": \"PR #$PR_NUMBER closed without merge\"}"
    ;;
  *)
    echo "{\"cron_status\": \"wait\"}"
    ;;
esac
```

### Pattern 4: External API call

```python
#!/usr/bin/env python3
# Lambda: notify-slack.py

import os
import json
import urllib.request

SLACK_WEBHOOK = os.environ.get('SLACK_WEBHOOK_URL')
MESSAGE = os.environ.get('NENJO_TICKET_TITLE', 'Task completed')

data = json.dumps({'text': MESSAGE}).encode('utf-8')
req = urllib.request.Request(
    SLACK_WEBHOOK,
    data=data,
    headers={'Content-Type': 'application/json'}
)

try:
    urllib.request.urlopen(req)
    print("Notification sent")
    exit(0)
except Exception as e:
    print(f"Failed to send notification: {e}")
    exit(1)
```

### Pattern 5: Database operation

```bash
#!/bin/bash
# Lambda: seed-database.sh

cd "$NENJO_GIT_WORK_DIR" || exit 1

# Run database migrations
npx prisma db push --accept-data-loss

if [ $? -eq 0 ]; then
  # Seed data
  npx prisma db seed
  
  if [ $? -eq 0 ]; then
    echo "Database seeded successfully"
    exit 0
  fi
fi

echo "Database seeding failed"
exit 1
```

## Debugging: my lambda fails silently

- **Check exit code** — Non-zero exits are treated as failures
- **Check stdout** — Output is captured as the step's `output` field
- **Check stderr** — Stderr is included in the output
- **Check environment** — Variables like `NENJO_GIT_WORK_DIR` may be missing if the routine wasn't triggered from a git context

## Debugging: timeout errors

Set a timeout in the step config:

```json
{
  "name": "Long Running Task",
  "step_type": "lambda",
  "lambda_id": "LAMBDA_UUID",
  "config": {
    "timeout": "30m"
  }
}
```

Default timeout is 5 minutes. For long operations, increase this value.
