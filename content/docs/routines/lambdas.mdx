---
title: Lambdas
description: Deterministic scripts that run without an LLM—write, store, and reuse scripts in your routines.
---

Your routine is built—now make it run. Sometimes you need to execute deterministic tasks that don't need an LLM—running tests, checking git status, calling APIs, or performing file operations. **Lambdas** are reusable scripts stored in the database and executed on the worker.

Think of lambdas as utility functions: they're reusable, parameterized, and run the same way every time.

## Data model

| Field | Type | Description |
|---|---|---|
| `id` | UUID | Unique identifier |
| `name` | string | Human-readable name |
| `description` | string? | Optional description |
| `path` | string | Relative path within `~/.nenjo/lambdas/` |
| `body` | string | The script source code |
| `interpreter` | string | How to execute: `auto`, `bash`, `sh`, `python3`, or `node` |
| `is_system` | boolean | Whether this is a built-in system lambda |
| `created_by` | UUID? | Owner user ID (null for system lambdas) |

### Interpreters

| Value | Description |
|---|---|
| `auto` | Execute directly (must have a shebang and be executable) |
| `bash` | Run with `/bin/bash` |
| `sh` | Run with `/bin/sh` |
| `python3` | Run with `python3` |
| `node` | Run with `node` |

Default is `auto`.

## Environment variables

When a lambda runs as part of a routine, the executor injects `NENJO_*` environment variables:

| Variable | Source |
|---|---|
| `NENJO_ROUTINE_ID` | Routine ID |
| `NENJO_STEP_ID` | Current step ID |
| `NENJO_STEP_NAME` | Current step name |
| `NENJO_PROJECT_ID` | Project ID |
| `NENJO_EXECUTION_RUN_ID` | Execution run ID |
| `NENJO_TICKET_ID` | Task ID |
| `NENJO_TICKET_TITLE` | Task title |
| `NENJO_TICKET_SLUG` | URL-safe task identifier |
| `NENJO_GIT_BRANCH` | Current working branch |
| `NENJO_GIT_TARGET_BRANCH` | Target branch for merges/PRs |
| `NENJO_GIT_WORK_DIR` | Worktree directory path |
| `NENJO_GIT_REPO_URL` | Remote repository URL |
| `NENJO_CONTEXT_FILE` | Path to JSON file with full routine context |
| `NENJO_GIT_COMMON_DIR` | Path to main `.git/` directory |

### Context file

A JSON file with the full routine context is written to a temporary path and available via `NENJO_CONTEXT_FILE`. Scripts that need structured data beyond environment variables can read from here.

## Exit codes

| Exit code | Result |
|---|---|
| `0` | `passed: true` |
| Non-zero | `passed: false` |

Stdout is captured as the step's `output` text.

## Step configuration

```json
{
  "name": "Run Tests",
  "step_type": "lambda",
  "lambda_id": "LAMBDA_UUID",
  "config": {
    "interpreter_override": "bash",
    "timeout": "10m"
  }
}
```

| Config field | Type | Default | Description |
|---|---|---|---|
| `lambda_id` | UUID | -- | Can also be set as top-level step field |
| `interpreter_override` | string | -- | Override the lambda's default interpreter |
| `timeout` | string | `"5m"` | Maximum execution time |

## Lambda script patterns

### Pattern 1: Git status check

Fail if there are uncommitted changes:

```bash
#!/bin/bash
# Lambda: check-git-status.sh

cd "$NENJO_GIT_WORK_DIR" || exit 1

if [ -n "$(git status --porcelain)" ]; then
  echo "Uncommitted changes detected:"
  git status --short
  exit 1
fi

echo "Working directory is clean"
exit 0
```

### Pattern 2: Run test suite

Run tests and exit with appropriate code:

```bash
#!/bin/bash
# Lambda: run-tests.sh

cd "$NENJO_GIT_WORK_DIR" || exit 1

echo "Running test suite..."
npm test

if [ $? -eq 0 ]; then
  echo "All tests passed"
  exit 0
else
  echo "Tests failed"
  exit 1
fi
```

### Pattern 3: Call external API

```bash
#!/bin/bash
# Lambda: fetch-data.sh

API_URL="https://api.example.com/data"
OUTPUT_FILE="$NENJO_GIT_WORK_DIR/data.json"

response=$(curl -s -w "%{http_code}" -o "$OUTPUT_FILE" "$API_URL")

if [ "$response" = "200" ]; then
  echo "Data fetched successfully"
  exit 0
else
  echo "API request failed with status: $response"
  exit 1
fi
```

### Pattern 4: Read context and make decision

```bash
#!/bin/bash
# Lambda: decide-route.sh

cd "$NENJO_GIT_WORK_DIR" || exit 1

# Read task complexity from context
COMPLEXITY=$(cat "$NENJO_CONTEXT_FILE" | python3 -c "import sys,json; print(json.load(sys.stdin).get('task',{}).get('complexity',0))")

if [ "$COMPLEXITY" -gt 8 ]; then
  echo "Complex task - route to senior reviewer"
  exit 0
else
  echo "Simple task - route to junior reviewer"
  exit 1
fi
```

### Pattern 5: PR merge check (for cron steps)

```bash
#!/bin/bash
# Lambda: check-pr-merged.sh
# For use in a cron step - polls until a PR is merged

cd "$NENJO_GIT_WORK_DIR" || exit 1

# Read PR number from context file
PR_NUMBER=$(cat "$NENJO_CONTEXT_FILE" | python3 -c "import sys,json; print(json.load(sys.stdin).get('pr_number',''))")

if [ -z "$PR_NUMBER" ]; then
  echo '{"cron_status": "abort", "reason": "No PR number in context"}'
  exit 0
fi

STATE=$(gh pr view "$PR_NUMBER" --json state -q '.state' 2>/dev/null)

case "$STATE" in
  MERGED)
    echo "{\"cron_status\": \"pass\", \"reason\": \"PR #$PR_NUMBER merged\"}"
    ;;
  CLOSED)
    echo "{\"cron_status\": \"fail\", \"reason\": \"PR #$PR_NUMBER closed without merge\"}"
    ;;
  *)
    echo "{\"cron_status\": \"wait\"}"
    ;;
esac
```

## API

Lambda routes are under `/api/v1/lambdas`.

### Create a lambda

```bash
curl -X POST \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Run Tests",
    "description": "Execute the project test suite",
    "path": "scripts/run-tests.sh",
    "body": "#!/bin/bash\nset -e\nnpm test",
    "interpreter": "bash"
  }' \
  https://your-instance.com/api/v1/lambdas
```

### List lambdas

```bash
curl -H "Authorization: Bearer $TOKEN" \
  https://your-instance.com/api/v1/lambdas
```

### Update a lambda

```bash
curl -X PATCH \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "body": "#!/bin/bash\nset -e\nnpm run test:ci"
  }' \
  https://your-instance.com/api/v1/lambdas/$LAMBDA_ID
```

### Delete a lambda

```bash
curl -X DELETE \
  -H "Authorization: Bearer $TOKEN" \
  https://your-instance.com/api/v1/lambdas/$LAMBDA_ID
```

## Integration with routines

### Lambda steps

Direct execution within the routine flow. The script runs once, exit code determines `on_pass` or `on_fail` edge.

### Cron steps in lambda mode

A cron step can use a lambda instead of an agent for polling. The lambda runs repeatedly at the configured interval and signals completion via `cron_status` JSON.

## Debugging: my lambda fails with "command not found"

1. **Use absolute paths** — Don't rely on PATH being set
2. **Check interpreter** — Ensure the lambda's interpreter matches your script
3. **Use `which`** — Add `which npm || which node || echo "not found"` to debug

## Debugging: my lambda hangs

1. **Check timeout** — Default is 5 minutes; increase in step config
2. **Check for interactive prompts** — Use `curl -s` not `curl` to avoid hanging
3. **Check network** — Ensure the worker can reach external services

## Debugging: my lambda runs but step fails

1. **Check exit code** — Non-zero = failure
2. **Check stdout** — The output is captured as the step's output
3. **Check stderr** — stderr is not captured; redirect to stdout if needed: `2>&1`
