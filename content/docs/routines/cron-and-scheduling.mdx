Your routine is built—now make it run. If you need a routine to run automatically—like an alarm clock going off at a set time—cron and scheduling is how you automate it.

Think of it this way:
- **Executions** are like cooking a recipe: you follow the steps once
- **Cron** is like setting an alarm: it triggers the routine to run on a schedule

## Two scheduling approaches

Nenjo supports two forms of scheduled execution:

| Approach | Scope | Use case |
|---|---|---|
| **Cron steps** | Single step within a routine | Polling/waiting for external events (e.g., wait for PR merge) |
| **Cron-triggered routines** | Entire routine | Recurring autonomous tasks (e.g., daily data sync) |

## Cron steps

A cron step is a routine step that repeatedly executes a function at a fixed interval until it signals completion or times out. This is useful for **polling external systems**—for example, waiting for a PR to be merged or a deployment to finish.

### Configuration

```json
{
  "step_type": "cron",
  "role_id": "ROLE_UUID",
  "config": {
    "interval": "30s",
    "timeout": "2h"
  }
}
```

| Field | Type | Default | Description |
|---|---|---|---|
| `interval` | string | `"60s"` | How often to run the function |
| `timeout` | string | `"24h"` | Maximum total time before the step aborts |
| `role_id` | UUID | -- | Agent role to run (agent mode) |
| `lambda_id` | UUID | -- | Lambda script to run (lambda mode) |

### Execution modes

- **Agent mode** — An LLM agent runs on each polling cycle using the specified role. Include a `cron_status` JSON signal in the output.
- **Lambda mode** — A script runs on each polling cycle. Communicate status via stdout.

### Signaling

On each cycle, parse the function's output for a status signal:

```json
{"cron_status": "pass", "reason": "PR #42 was merged successfully"}
```

| Status | Effect |
|---|---|
| `pass` | Stop the loop, take the `on_pass` edge |
| `fail` | Stop the loop, take the `on_fail` edge |
| `wait` | Sleep for `interval` and run again |
| `abort` | Abort the routine immediately with an error |

Legacy format: `CRON_DONE:PASS` and `CRON_DONE:FAIL` are also recognized.

### Real-world example: wait for PR merge

```json
{
  "name": "Wait for PR Merge",
  "step_type": "cron",
  "lambda_id": "LAMBDA_UUID",
  "config": {
    "interval": "5m",
    "timeout": "12h"
  }
}
```

The lambda script:
```bash
#!/bin/bash
PR_STATE=$(gh pr view "$NENJO_PR_NUMBER" --json state -q '.state')
if [ "$PR_STATE" = "MERGED" ]; then
  echo '{"cron_status": "pass", "reason": "PR merged"}'
elif [ "$PR_STATE" = "CLOSED" ]; then
  echo '{"cron_status": "fail", "reason": "PR was closed without merging"}'
else
  echo '{"cron_status": "wait"}'
fi
```

This step polls every 5 minutes for up to 12 hours. When the PR merges, it takes the `on_pass` edge to continue the routine.

## Cron-triggered routines

Entire routines can be triggered on a recurring schedule. This is managed by the **CronManager** on the worker—think of it as a scheduler service that keeps track of all your alarm clocks.

### Routine configuration

Set the routine's `trigger` to `cron` and add a `schedule`:

```bash
curl -X POST \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Daily Code Audit",
    "trigger": "cron",
    "metadata": {
      "schedule": "0 9 * * *"
    }
  }' \
  https://your-instance.com/api/v1/routines
```

### Schedule format

**Cron expressions** — Standard 5-field syntax (minute, hour, day-of-month, month, day-of-week):

| Expression | Meaning |
|---|---|
| `0 9 * * *` | Every day at 9:00 AM |
| `*/30 * * * *` | Every 30 minutes |
| `0 0 * * 1` | Every Monday at midnight |

**Interval strings** — Simple duration strings:

| Interval | Meaning |
|---|---|
| `30s` | Every 30 seconds |
| `5m` | Every 5 minutes |
| `1h` | Every hour |
| `2d` | Every 2 days |

The format is auto-detected: spaces = cron expression, otherwise = interval.

### Real-world example: scheduled data sync

```bash
# Create a daily data sync routine
curl -X POST \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Daily Sales Data Sync",
    "trigger": "cron",
    "metadata": {
      "schedule": "0 2 * * *"
    },
    "steps": [
      {
        "id": "fetch-sales",
        "name": "Fetch Sales Data",
        "step_type": "lambda",
        "lambda_id": "LAMBDA_UUID",
        "edges": [{"target": "transform-data", "condition": "on_pass"}]
      },
      {
        "id": "transform-data",
        "name": "Transform and Load",
        "step_type": "lambda",
        "lambda_id": "LAMBDA_UUID_2",
        "edges": [{"target": "notify-complete", "condition": "on_pass"}]
      },
      {
        "id": "notify-complete",
        "name": "Notify Team",
        "step_type": "agent",
        "agent_id": "AGENT_UUID",
        "edges": []
      }
    ]
  }' \
  https://your-instance.com/api/v1/routines
```

This routine runs every day at 2 AM:
1. **Fetch Sales Data** — Lambda pulls data from the sales API
2. **Transform and Load** — Lambda cleans and loads data into the warehouse
3. **Notify Team** — Agent sends a summary to Slack/email

### Manual trigger

You can manually trigger a cron routine (fires immediately without affecting the schedule):

```bash
curl -X POST \
  -H "Authorization: Bearer $TOKEN" \
  https://your-instance.com/api/v1/routines/$ROUTINE_ID/trigger
```

Returns `202 Accepted`.

## CronManager

The CronManager runs on the worker and manages all cron-triggered schedules.

### Operations

| Operation | Event | Description |
|---|---|---|
| Enable | `cron.enable` | Start a new schedule timer |
| Disable | `cron.disable` | Cancel the timer |
| Trigger now | `cron.trigger` | Fire immediately without affecting schedule |

### Router events

The backend pushes events to the worker:

```json
{"type": "cron.enable", "assignment_id": "...", "routine_id": "...", "project_id": "...", "schedule": "0 9 * * *"}
```

```json
{"type": "cron.disable", "assignment_id": "..."}
```

```json
{"type": "cron.trigger", "routine_id": "...", "project_id": "..."}
```

### Heartbeat tracking

| Field | Description |
|---|---|
| `assignment_id` | The assignment or routine ID |
| `routine_id` | The routine being scheduled |
| `last_run_at` | Timestamp of last execution |
| `next_fire_at` | Computed next fire time |

## Cron steps vs. cron routines

| Feature | Cron step | Cron routine |
|---|---|---|
| Scope | Single step within a routine | Entire routine |
| Trigger | Runs as part of routine execution | Runs on its own schedule |
| Use case | Polling/waiting within a workflow | Recurring autonomous tasks |
| Signal | Function signals pass/fail/wait/abort | Routine completes normally |
| Manager | Executor loop | CronManager on worker |

## Debugging: my scheduled routine didn't run

1. **Check schedule syntax** — Use a cron parser to verify your expression
2. **Check worker logs** — The CronManager logs when timers fire
3. **Check routine validity** — Run [DAG validation](/docs/routines/dag-validation)
4. **Check cron.enable event** — Ensure the backend sent the enable event to the worker

## Debugging: my cron step times out

1. **Check timeout value** — Default is 24h; increase if needed
2. **Check interval** — Too-frequent polling may hit rate limits
3. **Check external system** — The service being polled may be unavailable
