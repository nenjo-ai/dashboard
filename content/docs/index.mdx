Nenjo is a system for turning AI from a single chat box into a working environment.

It gives you a place to design agents, give them useful context, connect them to tools, route work through repeatable workflows, and keep a record of what happened. Instead of asking one assistant to remember everything and improvise every step, Nenjo lets you shape the people, permissions, knowledge, and process around the work.

At the center of the platform is **Nenji**, the default guide and orchestrator. Nenji helps you create resources, explain how they fit together, inspect existing configuration, and move between high-level design and concrete platform actions.

## Why Nenjo exists

Most teams do not just need an AI model. They need a way to make AI behavior understandable, repeatable, and connected to real work.

Nenjo is built around a few practical ideas:

- Agents should have clear roles, prompts, memory, tools, and permission boundaries.
- Important work should run through workflows that can be inspected and improved.
- Project knowledge should live somewhere structured instead of being scattered across chat history.
- Sensitive actions should require explicit modes, scopes, and audit trails.
- Developers should be able to use the same concepts from the hosted platform or from code.

That makes Nenjo useful for work like product planning, code review, compliance review, research, operations, support workflows, and any setting where AI needs context, structure, and accountability.

## Two ways to use Nenjo

Nenjo has two main surfaces.

**The platform** is the hosted product: dashboard, chat, project pages, document editors, routine builder, agent builder, settings, workers, and platform tools. This is where most users create and operate Nenjo resources without writing manifests by hand.

**The SDK** is the embeddable developer surface: local manifests, Rust runtime APIs, model providers, tool providers, prompt context, memory, worker composition, and transport contracts. This is for teams building Nenjo-powered systems directly into their own applications or infrastructure.

The same core ideas exist in both places. If you are working in the dashboard or asking Nenji to configure something, think in terms of platform resources and editors. If you are embedding Nenjo in code, think in terms of manifests and runtime APIs.

## The core model

Nenjo is made from resources that fit together. A project holds the work and knowledge. Agents do the work. Routines make the work repeatable. Abilities give agents focused specialist tools. Domains let users intentionally switch an agent into a different mode when the work needs different guidance, permissions, or auditability.

You can start with only a project and an agent. As the work becomes more serious, add structure where it helps: routines for repeatability, abilities for specialist work, domains for explicit high-trust modes, and Library knowledge for durable source material.

For the resource-by-resource view, see [Building Blocks](/docs/introduction/building-blocks).
