Nenjo is built from a set of resources that compose together. Each one has a simple job: hold context, define behavior, grant a capability, switch modes, run a process, or preserve knowledge.

You do not need all of them on day one. Most useful setups begin with a project and an agent, then add routines, abilities, domains, memory, and documents as the work becomes more important or more repeatable.

## Projects

Projects are the main boundary for work in Nenjo. A project keeps tasks, documents, settings, execution history, repository connections, and project-specific memory together.

Think of a project as a working environment, not just a folder. It gives agents a place to understand what they are working on, which documents matter, what has already happened, and how future executions should be scoped.

The important layer is project knowledge. Projects can contain structured documents that form a local knowledge graph:

- **Domain** documents explain the problem space.
- **Entity** documents define important objects and data models.
- **Policy** documents capture rules, constraints, and decision criteria.
- **Taxonomy** documents classify concepts.
- **Reference** documents store facts, glossaries, and lookup material.
- **Guide** documents explain patterns and usage.

When those documents are connected, agents can reason from shared project context instead of relying only on the current chat. For code-backed projects, a repository connection can also give executions an isolated workspace where agents inspect, change, test, and report on real files.

## Agents

Agents are the main behavioral units in Nenjo. An agent defines a role: how work should be interpreted, which prompts shape behavior, what memory matters, which model to use, which tools are available, and what permissions apply.

An agent can be conversational, task-focused, scheduled, evaluative, or part of a multi-agent collaboration. The role stays consistent, but the runtime context changes depending on how the agent is being used.

**What an agent owns:**
- Behavioral identity and role
- Prompt configuration (system + developer prompts + mode-specific templates)
- Memory profile (core, project, shared focus)
- Model assignment
- Platform scopes (permissions)
- Assigned abilities (specialist tools)
- Assigned domains (user-activated modes)
- Assigned MCP servers (external tools)

**Runtime modes:**
| Mode | Description |
|------|-------------|
| `chat` | Conversational interaction with a user |
| `task` | Execution of a project task with full context |
| `gate` | Evaluation of evidence against acceptance criteria |
| `cron` | Scheduled/recurring execution |
| `heartbeat` | Periodic autonomous checks |

Start with a clear role and the smallest useful capability set. Add tools, scopes, domains, and memory focus deliberately as the agent's responsibility grows.

## Abilities

Abilities are reusable specialist capabilities that an agent can invoke as tools. They are for focused work that is useful across agents but does not need to become a full standalone agent or a user-facing mode.

An ability might handle code review, document summarization, policy checks, data extraction, research synthesis, or another narrow task. The calling agent decides whether to use it based on the current request and the ability's activation guidance.

Use an ability when the agent can safely decide to call a specialist tool. If the user should explicitly opt into the behavior, use a domain instead.

---

## Domains

Domains are user-activated modes. They let a user intentionally place an agent into a different operating state for a session.

A domain can change the agent's guidance, expose additional abilities, add MCP integrations, or grant expanded platform scopes through a controlled path. Domains are designed for work where the mode switch should be visible, intentional, and auditable.

Common examples include compliance mode, production mode, legal review mode, debug mode, or executive summary mode.

The distinction from abilities matters: abilities are agent-invoked; domains are user-activated. Use a domain when the work is sensitive, elevated, strategic, or should leave a clear audit trail.

---

## Routines

Routines make work repeatable. A routine is a workflow graph made from steps, gates, agents, councils, triggers, and terminal outcomes.

Use a routine when the work has a process: draft then review, fan out to several specialists then synthesize, run a scheduled check, or gate an output against acceptance criteria. Every step transition and decision can be recorded, which makes routines easier to inspect and improve than a long unstructured chat.

**Components:**
- **Steps** — Individual actions or agent invocations
- **Gates** — Conditional checks that evaluate evidence
- **Agents** — Behavioral units that process work
- **Councils** — Multi-agent collaboration groups
- **Triggers** — Events that initiate or control flow
- **Terminals** — End states (success, failure, blocked)

**Patterns:**
- Linear pipeline (step → step → step)
- Conditional routing (gate → agent)
- Parallel execution (multiple agents simultaneously)
- Council with leader and members
- Retry loops with gates

## Memory

Nenjo provides a **scoped memory system** for agents with three scopes:

| Scope | What It Stores | Typical Use |
|-------|---------------|-------------|
| `core_focus` | Long-term, cross-project knowledge | Personality, methodology, core principles |
| `project_focus` | Knowledge specific to one project | Task history, decisions, documents |
| `shared_focus` | Knowledge shared across projects | Reusable patterns, team conventions |

**Best practice:** Start simple with only `project_focus`. Expand to `core_focus` and `shared_focus` as the agent's responsibilities grow.

## Context Blocks

Context blocks are **reusable prompt-context assets** referenced by path-like template names. They allow common prompt patterns to be defined once and reused across many agents.

**Use cases:**
- System instructions shared across agent types
- Common tool definitions
- Standard output formats
- Reusable guidance snippets

**Example reference:** `context:standard/instructions/security`

---

## Template Variables

Template variables connect **static prompt design** with **live execution state**. They are injected at runtime to provide current context.

**Common variables:**
| Variable | Description |
|----------|-------------|
| `{{ project }}` | Current project context |
| `{{ project.documents }}` | Project knowledge and document metadata |
| `{{ task }}` | Current task context |
| `{{ task.acceptance_criteria }}` | Task acceptance criteria |
| `{{ chat.message }}` | User message in chat mode |
| `{{ routine }}` | Current routine context |
| `{{ routine.execution_id }}` | Current routine execution run |
| `{{ available_agents }}` | Agents available for delegation or routing |
| `{{ memories.project }}` | Learned project-specific memory |

## Scopes

Scopes define **fine-grained permissions** for platform resource families. They follow a least-privilege model where agents receive only the platform tool access they need.

Each scope adds a corresponding set of platform tools to an agent, ability, domain, API key, or organization member. For example, `agents:read` allows agent read/list/get tools, while `agents:write` allows tools that create or mutate agents. Write scopes imply read access for the same resource family.

**Scope examples:**
- `agents:read` / `agents:write` — Read or mutate agents, including prompt-related agent surfaces
- `abilities:read` / `abilities:write` — Read or mutate abilities
- `domains:read` / `domains:write` — Read or mutate domains and domain sessions
- `projects:read` / `projects:write` — Read or mutate projects, tasks, documents, dependencies, executions, and project-scoped state
- `routines:read` / `routines:write` — Read or mutate routines
- `councils:read` / `councils:write` — Read or mutate councils
- `context_blocks:read` / `context_blocks:write` — Read or mutate reusable prompt-context assets
- `models:read` / `models:write` — Read or mutate model records

Platform scopes are assigned by admin or platform-controlled surfaces, not by agent-facing creation tools. Agents may recommend the minimum scopes needed, but they should not assign scopes to themselves.

## How They Fit Together

These building blocks compose into a complete system:

```
Nenjo Workspace
├── Projects
│   ├── Tasks & executions
│   ├── Documents / knowledge graph
│   ├── Repository context
│   └── Project-scoped memory
│
├── Agents
│   ├── Prompt configuration
│   ├── Model assignment
│   ├── Memory profile
│   ├── Platform scopes
│   ├── Assigned abilities
│   ├── Assigned domains
│   └── Assigned MCP servers
│
├── Routines
│   ├── Triggers
│   ├── Steps
│   ├── Gates
│   ├── Agent and council runs
│   └── Terminal outcomes
│
├── Abilities
│   └── Specialist tools agents can invoke
│
├── Domains
│   └── User-activated modes with extra guidance, scopes, tools, or abilities
│
├── Councils
│   └── Structured multi-agent collaboration
│
├── Context Blocks
│   └── Reusable prompt-context assets
│
└── Models and MCP Servers
    └── Runtime integrations assigned to agents, abilities, or domains
```
