Domains are activatable overlays that temporarily modify an agent's behavior, tool access, and platform permissions. When a domain is active, it layers its configuration on top of the role's existing setup.

## Domain Manifest

Every domain has a manifest (stored as JSONB) that defines its behavior:

```json
{
  "schema_version": 1,
  "domain_type": "authoring",
  "prompt": {
    "system_addon": "You are now in PRD authoring domain...",
    "guidelines": [
      "Ask clarifying questions before each section",
      "Focus on user problems, not solutions"
    ],
    "entry_message": "Let's create a PRD. What problem are you solving?",
    "exit_message": "Your PRD has been saved."
  },
  "tools": {
    "allow": ["file_read", "file_write", "web_search_tool"],
    "deny": ["shell"],
    "additional_scopes": ["tasks:write"],
    "activate_mcp": ["github"]
  },
  "artifact": {
    "type": "document",
    "format": "markdown",
    "filename_template": "prd-{{slugify(title)}}.md",
    "output_template": "# {{title}}\n\n{{content}}"
  },
  "session": {
    "max_turns": 50,
    "auto_save_interval": 5,
    "exit_commands": ["/exit", "/done", "/finish"]
  }
}
```

## Domain Types

The `mode_type` field classifies the domain's purpose:

| Type | Description |
|------|-------------|
| `authoring` | Creating structured documents (PRDs, specs, reports) |
| `investigation` | Research and analysis tasks |
| `review` | Reviewing code, documents, or work output |
| `custom` | User-defined purpose |

## Prompt Configuration

The `prompt` block is additive to the role's existing system prompt:

| Field | Type | Description |
|-------|------|-------------|
| `system_addon` | string or null | Text appended to the system prompt while the domain is active |
| `guidelines` | string[] | Additional behavioral guidelines |
| `entry_message` | string or null | Message shown when the domain is activated |
| `exit_message` | string or null | Message shown when the domain is exited |

## Tool Configuration

The `tools` block controls which tools are available during the domain:

### Allow / Deny Lists

```json
{
  "allow": ["file_read", "file_write", "shell"],
  "deny": ["http_request"]
}
```

- **`allow`** -- If non-empty, only these tools are available (whitelist). Tools not in the list are excluded.
- **`deny`** -- These tools are explicitly excluded (blacklist). Applied after the allow list.

If both are empty, the role's default tool set is used unchanged.

### Scope Escalation

The `additional_scopes` field temporarily grants the agent additional [platform scopes](/docs/agents/roles#platform-scopes) for the duration of the domain:

```json
{
  "additional_scopes": ["tasks:write", "routines:write"]
}
```

This is how domains like `/the-creator` can grant write access to platform resources that the role normally only has read access to. The escalated scopes are merged with the role's base `platform_scopes` when fetching MCP tools.

### MCP Server Activation

The `activate_mcp` field enables external MCP servers by name for the duration of the domain:

```json
{
  "activate_mcp": ["github", "linear"]
}
```

These servers must be [configured](/docs/agents/mcp-integration#external-mcp-servers) in the platform. The domain activation adds them to the agent's tool set alongside any MCP servers already assigned to the role.

## Artifact Configuration

Domains can produce structured output artifacts:

| Field | Type | Description |
|-------|------|-------------|
| `type` | string | Artifact type (default: `"document"`) |
| `format` | string | Output format: `markdown`, `json`, `yaml`, or `html` |
| `filename_template` | string or null | Template for the output filename |
| `schema` | object or null | JSON Schema for structured artifact data |
| `output_template` | string or null | Handlebars-style template for rendering the final artifact |

Filename templates support `{{key}}` and `{{slugify(key)}}` placeholders that are resolved from the artifact draft data.

## Session Configuration

| Field | Type | Default | Description |
|-------|------|---------|-------------|
| `max_turns` | number | `50` | Maximum conversation turns (1--200) |
| `auto_save_interval` | number | `5` | Save draft every N turns |
| `exit_commands` | string[] | `["/exit", "/done", "/finish"]` | Commands that end the session |

Exit commands must start with `/`.

## Session Lifecycle

Domain sessions track the state of a mode activation:

1. **Create** -- A session is created when a domain is activated for a project + role
2. **Active** -- The agent operates with the domain's overlay; artifact drafts are saved periodically
3. **Complete** -- The session ends, artifact drafts are finalized and uploaded to S3
4. **Cancel** -- The session is abandoned without finalizing artifacts

When a session completes with an artifact draft, the system:
- Renders the draft through the `output_template` (if configured)
- Generates the filename from `filename_template`
- Uploads the rendered content to object storage
- Creates a `project_documents` record
- Creates a `domain_artifacts` record linking the session to the document

## API Endpoints

### Domain CRUD

```bash
# List all domains
curl -H "Authorization: Bearer $TOKEN" \
  https://your-instance.com/api/v1/domains

# Create a domain
curl -X POST -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"name": "prd", "display_name": "PRD Authoring", "command": "/prd"}' \
  https://your-instance.com/api/v1/domains

# Upload a domain from file
curl -X POST -H "Authorization: Bearer $TOKEN" \
  -F "file=@prd-domain.md" \
  https://your-instance.com/api/v1/domains/upload

# Reset a system-derived domain to the default template
curl -X POST -H "Authorization: Bearer $TOKEN" \
  https://your-instance.com/api/v1/domains/:id/reset
```

### Role-Domain Assignments

```bash
# List domains assigned to a role
curl -H "Authorization: Bearer $TOKEN" \
  https://your-instance.com/api/v1/agents/:id/domains

# Assign a domain to a role
curl -X POST -H "Authorization: Bearer $TOKEN" \
  https://your-instance.com/api/v1/agents/:id/domains/:domain_id

# Remove a domain from a role
curl -X DELETE -H "Authorization: Bearer $TOKEN" \
  https://your-instance.com/api/v1/agents/:id/domains/:domain_id

# Toggle or update a domain assignment
curl -X PATCH -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"enabled": true}' \
  https://your-instance.com/api/v1/agents/:id/domains/:domain_id
```

### Sessions

```bash
# Create a domain session
curl -X POST -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"project_id": "...", "role_id": "..."}' \
  https://your-instance.com/api/v1/domains/:id/sessions

# Get active session for a project + role
curl -H "Authorization: Bearer $TOKEN" \
  "https://your-instance.com/api/v1/domains/sessions/active?project_id=...&role_id=..."

# Complete session
curl -X POST -H "Authorization: Bearer $TOKEN" \
  https://your-instance.com/api/v1/domains/sessions/:sid/complete

# Cancel session
curl -X POST -H "Authorization: Bearer $TOKEN" \
  https://your-instance.com/api/v1/domains/sessions/:sid/cancel
```

## Upload Formats

Domains can be uploaded as `.md`, `.json`, or `.yaml` files (5 MB limit). The markdown format uses YAML frontmatter with the body becoming `prompt.system_addon`:

```markdown
---
name: prd
display_name: PRD Authoring
command: /prd
description: Create product requirement documents
domain_type: authoring
tools:
  allow: ["file_read", "file_write"]
artifact:
  type: document
  format: markdown
  filename_template: "prd-{{slugify(title)}}.md"
---

You are now in PRD authoring domain. Help the user create a comprehensive product requirements document.

## Guidelines
- Ask clarifying questions before each section
- Focus on user problems, not solutions
```
