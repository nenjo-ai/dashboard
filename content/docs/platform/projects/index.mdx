# Projects

A **project** is the workspace boundary for a body of work in Nenjo. It groups tasks, settings, repository connection, execution history, and project-scoped memory so agents know what they are working on.

Use separate projects when the work has different goals, repository context, task history, or execution state. Put source material, policies, references, and durable documentation in the [Library](/docs/platform/library), then reference that Library knowledge from project prompts and agents.

## What a project contains

| Part | What it does |
|------|--------------|
| Identity | Name, slug, description, and timestamps |
| Settings | Project context, metadata, repository settings, and other project-level configuration |
| Tasks | Work items with status, priority, type, acceptance criteria, and optional routine assignment |
| Repository | Optional Git repository URL, target branch, and sync status |
| Executions | Runs associated with tasks, agents, routines, and schedules |
| Memory scope | Project-specific learned context for agents that use project memory |

Projects are organization resources. Project APIs and project-backed agent tools are controlled by `projects:read` and `projects:write`.

## Dashboard shape

The dashboard project detail page has five main tabs:

| Tab | Purpose |
|-----|---------|
| Tasks | Create, filter, inspect, update, and delete project tasks |
| Context | Store global guidance shared with agents working in the project |
| Execution | Inspect project execution runs and step progress |
| Settings | Manage repository sync settings and custom metadata |

## Runtime shape

When an agent runs inside a project, Nenjo can provide:

- Project identity such as `{{ project.name }}` and `{{ project.description }}`
- Project settings and metadata
- Project-specific memory focus
- Git context when the project repository is synced
- Task and routine context when the run is task-driven or routine-driven
- Library knowledge indexes through `{{ lib.<pack_slug> }}` when a prompt includes them

This is why project setup matters. A well-described project with clear tasks, useful Library references, and a synced repository gives agents a much better starting point than an empty container.
