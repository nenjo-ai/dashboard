# Prompt Templating

Prompt templates let an agent keep reusable instructions while still receiving the current task, project, chat message, routine step, memory, and available capabilities.

Nenjo uses `{{ variable.name }}` syntax. At runtime, the worker renders those variables into text or XML-like blocks before sending the prompt to the model.

## Main variable groups

The template variable list in the dashboard comes from the Nenjo SDK. These are the groups you will use most often:

| Group | Examples | Use it for |
|-------|----------|------------|
| Agent | `{{ self }}`, `{{ agent.name }}`, `{{ agent.description }}` | Role and identity |
| Chat | `{{ chat.message }}` | User chat turns |
| Task | `{{ task }}`, `{{ task.title }}`, `{{ task.acceptance_criteria }}` | Project task execution |
| Project | `{{ project }}`, `{{ project.context }}`, `{{ project.working_dir }}` | Project-aware work |
| Knowledge | `{{ lib.product_docs }}`, `{{ pkg.nenjo_ai.packages.knowledge.core }}` | Discovering Library or package knowledge material |
| Routine | `{{ routine }}`, `{{ routine.step.name }}`, `{{ routine.execution_id }}` | Routine steps |
| Gate | `{{ gate.previous_output }}` | Evaluation steps |
| Heartbeat | `{{ heartbeat.previous_output }}`, `{{ heartbeat.last_run_at }}` | Periodic checks |
| Git | `{{ git }}`, `{{ git.current_branch }}`, `{{ git.work_dir }}` | Repository work |
| Memory | `{{ memories }}`, `{{ memories.project }}`, `{{ memory_profile }}` | Retrieved memory and focus lists |
| Artifacts | `{{ artifacts }}`, `{{ artifacts.project }}` | Saved generated outputs or workspace files |

The dashboard variable picker shows the current canonical list and can insert variables into prompt editors.

## Context blocks

Context blocks are reusable prompt snippets stored as organization resources. Their content is encrypted, but their names and paths are metadata.

A block with:

- `path`: `coding`
- `name`: `git_worktree`

is referenced as:

```jinja
{{ context.coding.git_worktree }}
```

Package-installed context blocks use the package namespace:

```jinja
{{ pkg.nenjo_ai.packages.context.tools.tool_usage }}
{{ pkg.nenjo_ai.packages.context.operations.write_discipline }}
```

Use context blocks for guidance that should be shared by several agents, such as team review standards, git workflow rules, or common decision principles.

## Knowledge traversal in prompts

Knowledge variables should tell the agent where source material exists, not provide the whole answer. When a prompt includes Library or package knowledge, include an instruction to search, read, and traverse outgoing edges before making source-backed claims:

```jinja
Knowledge index:
{{ lib.product_docs }}

For source-backed answers, search the knowledge pack, read the selected
documents, then follow outgoing neighbor edges when the selected document points
to policy, taxonomy, scope, or dependency material needed for the answer.
```

This is especially important for graph-shaped packs. Search usually finds a seed document; outgoing edges tell the agent which adjacent documents the author expected it to inspect next.

## Practical examples

Chat template:

```jinja
User request:
{{ chat.message }}

Relevant memory:
{{ memories.core }}
```

Task template:

```jinja
Task:
{{ task }}

Project:
{{ project }}

Knowledge index:
{{ lib.product_docs }}

Repository rules:
{{ context.coding.git_worktree }}
```

Gate template:

```jinja
Evidence:
{{ gate.previous_output }}

Task acceptance criteria:
{{ task.acceptance_criteria }}

Routine step:
{{ routine.step.instructions }}
```

## What to avoid

- Putting every variable into every template
- Injecting package knowledge indexes into simple chat turns when they are not relevant
- Treating memory as the source of truth when knowledge docs already contain the facts
- Referencing an ability or domain that is not assigned to the agent
- Hard-coding project-specific details in the system prompt
- Treating knowledge indexes as full document bodies
