# Prompt Configuration

An agent's **prompt configuration** is its behavior definition. It is edited through a dedicated prompt endpoint instead of being mixed into normal agent metadata updates.

Prompt configuration is org-scoped encrypted content. The dashboard encrypts it before sending it to the platform, and the platform stores the encrypted payload alongside a plaintext fallback shape used by older or unencrypted records.

## What is in prompt configuration

| Field | Purpose |
|-------|---------|
| `system_prompt` | Stable identity, role, boundaries, and high-level operating rules |
| `developer_prompt` | Practical working guidance, standards, and tool-use instructions |
| `templates.chat` | User-message wrapper for chat turns |
| `templates.task` | Task-execution wrapper for project work |
| `templates.gate` | Evaluation wrapper for pass/fail checks |
| `templates.cron` | Scheduled-run wrapper for cron routine steps |
| `templates.heartbeat` | Periodic maintenance wrapper for heartbeat runs |
| `memory_profile` | Focus lists that guide memory extraction and retrieval |

The system prompt and developer prompt are rendered with the same template variables as task templates, so they can include context blocks and live workspace data when appropriate.

## System prompt

Use the system prompt for the most durable parts of the agent:

- Role and responsibility
- Behavioral boundaries
- Communication expectations
- Policies that should not change by task
- The agent's relationship to projects, tools, and users

Keep it short enough that it can remain stable across many runs.

## Developer prompt

Use the developer prompt for guidance that is important but more likely to evolve:

- Team conventions
- Tool-use preferences
- Review or implementation methodology
- How to interpret available knowledge and artifacts
- When to delegate or use abilities

This is usually where most day-to-day behavior tuning belongs.

## Templates

Templates are the runtime wrappers around the current situation.

| Template | Typical contents |
|----------|------------------|
| Chat | `{{ chat.message }}`, relevant context blocks, and conversational instructions |
| Task | `{{ task }}`, `{{ project }}`, `{{ project.context }}`, git context, and acceptance criteria |
| Gate | `{{ gate.criteria }}` and `{{ gate.previous_output }}` |
| Cron | Routine metadata and instructions for scheduled work |
| Heartbeat | Previous output, last run time, and next run time |

If a template is empty, the runner can fall back to simpler runtime content. A good template is specific enough to focus the agent without dumping every possible variable into every run.

## Locking

Agents have a `prompt_locked` flag. When the prompt is locked, prompt updates are rejected until it is unlocked. Use this for agents whose behavior should not drift accidentally.

Locking affects prompt edits. It does not make unrelated metadata, model assignment, or resource assignments immutable.

## Previewing prompts

The prompt preview endpoint renders:

- The system prompt
- The developer prompt
- Sample user messages for chat, task, gate, cron, and heartbeat modes
- Assigned domain guidance
- Assigned ability prompts

Preview is useful before saving a change because it shows whether template variables and context blocks resolve the way you expect.

## Good prompt structure

Start with:

```jinja
You are {{ agent.name }}.

Role:
{{ agent.description }}

Operating guidance:
{{ custom.team.standards }}
```

Then keep runtime details in the matching template:

```jinja
User request:
{{ chat.message }}
```

```jinja
Task:
{{ task }}

Project:
{{ project }}

Project context:
{{ project.context }}
```
