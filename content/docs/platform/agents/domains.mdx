# Domains

A **domain** is a user-activated mode for an agent. It lets the user say, "operate in this context now," and Nenjo adds the domain's guidance and capabilities to the active session.

Domains are useful for explicit mode changes: production work, compliance review, legal review, architecture planning, debugging, or any other situation where the user should deliberately opt in.

## What a domain contains

| Field | What it means |
|-------|---------------|
| `name` | Internal identifier |
| `path` | Folder path used in the domain library |
| `display_name` | Human-friendly label |
| `description` | What the mode is for |
| `command` | The command or selector used to activate the domain |
| Guidance | Encrypted developer-prompt add-on for the active agent |
| `platform_scopes` | Additional Nenjo scopes available while the domain is active |
| `ability_ids` | Abilities made available in the domain |
| `mcp_server_ids` | MCP servers made available in the domain |
| Session config | Optional session behavior such as max turns and exit commands |

Domain guidance is org-scoped encrypted content. Domain metadata, commands, scopes, assignments, and session records are not encrypted.

## How activation works

When a user activates a domain for an agent:

1. Nenjo creates or finds the active domain session for that user, agent, and project.
2. The domain's guidance is added to the agent's prompt context.
3. The domain's scopes, abilities, and MCP servers become available for that session.
4. The session remains active until it is completed, cancelled, or replaced.

The active domain is session state, not a permanent change to the agent. Leaving the domain returns the agent to its normal behavior and assignments.

## Domain vs ability

| Question | Domain | Ability |
|----------|--------|---------|
| Who activates it? | The user | The agent |
| What does it change? | Mode, guidance, available scopes, tools, and abilities | A focused specialist execution |
| How long does it last? | Across a domain session | For a nested call |
| Best use | Explicit elevated or specialized mode | Reusable task-specific capability |

If the user should be aware that the agent is operating differently, use a domain.

## Designing domains

Good domains are explicit and understandable:

- The command should be easy to recognize, such as `/production` or `/legal-review`
- The description should say what changes when the mode is active
- The guidance should explain how the agent should behave differently
- Additional scopes should be limited to what the mode needs
- Added abilities should match the mode's purpose

Avoid using domains as a hidden permission shortcut. A domain is a user-visible mode, so it should be clear why it exists.
