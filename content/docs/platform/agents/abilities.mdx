# Abilities

An **ability** is a focused specialist behavior that an agent can call during a run. It is useful when a capability should be reusable, narrow, and available as a tool rather than becoming a full agent.

Abilities are organization resources. They can be assigned to agents and can also be added by active domains.

## What an ability contains

| Field | What it means |
|-------|---------------|
| `name` | Internal identifier |
| `tool_name` | The tool name exposed to the calling agent |
| `path` | Folder path used in the ability library |
| `display_name` | Human-friendly label |
| `description` | What the ability does |
| `activation_condition` | When the calling agent should consider using it |
| Developer prompt | Encrypted specialist instructions used during the ability run |
| `platform_scopes` | Nenjo resource scopes available to the ability |
| `mcp_server_ids` | MCP servers available during the ability run |
| `tool_filter` | Optional filter for limiting tool access |

The developer prompt is stored as org-scoped encrypted content. Ability metadata, scopes, MCP assignments, path, and activation condition are not encrypted.

## How abilities run

When an agent calls an ability:

1. The ability runs as a nested specialist execution.
2. It receives relevant task, project, chat, and memory context from the parent run.
3. It uses the ability's developer prompt as the specialist guidance.
4. Its available platform tools are filtered by the ability's scopes.
5. It returns a result to the calling agent.

From the user's point of view, an ability is part of the agent's work. From the agent's point of view, it is a callable tool with a clearer contract than free-form delegation.

## Ability vs agent

Use an ability when the work is a reusable sub-skill:

- Review this code for security issues
- Extract structured data from a document
- Evaluate this output against a policy
- Convert this content into a specific format

Use a separate agent when the work needs an ongoing identity, its own model assignment, or a broader role in routines and councils.

## Ability vs domain

| Question | Ability | Domain |
|----------|---------|--------|
| Who activates it? | The agent calls it as a tool | The user activates it as a mode |
| How broad is it? | Narrow and task-shaped | Broader behavior or permission shift |
| Where does guidance go? | Ability developer prompt | Domain guidance added to the active agent |
| What is it best for? | Specialist execution | Explicit mode changes |

If a capability should only be used after the user chooses a mode, make it a domain. If the agent can safely decide when to use it, make it an ability.

## Designing abilities

Good abilities have:

- A tool name that reads like an action, such as `review_security` or `extract_requirements`
- A short activation condition
- A clear expected output shape
- Minimal platform scopes
- Only the MCP servers needed for that specialist work

Avoid broad abilities like "do engineering work". That should usually be an agent or a routine.
