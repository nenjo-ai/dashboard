# Agents

An **agent** is the behavior profile Nenjo uses when work runs. It tells Nenjo what role the agent plays, which model powers it, what instructions shape its behavior, and which tools or platform resources it can use.

Agents are organization resources. Team members can create custom agents, edit their metadata, assign models, attach abilities and domains, and decide which platform scopes the agent receives.

## What an agent contains

| Part | What it does |
|------|--------------|
| Identity | `name`, optional `display_name`, description, and color |
| Model assignment | The model record used when this agent runs |
| Prompt configuration | System prompt, developer prompt, task templates, and memory focus |
| Platform scopes | The Nenjo resource permissions available to the agent |
| Abilities | Specialist tools the agent may call during a run |
| Domains | User-activated modes that add temporary guidance and capabilities |
| MCP servers | External tool servers assigned to the agent |
| Heartbeat | Optional scheduled check-in behavior for autonomous maintenance |

The prompt configuration is stored separately from the rest of the agent metadata. In normal use it is encrypted with the organization content key. Metadata such as the agent name, description, model ID, scopes, and assignments is not encrypted.

## System and custom agents

Nenjo ships with system agent templates. When an organization is set up, those templates are copied into the organization so they can be used like normal agents.

System-derived copies keep a link back to their template. They can be reset to the template defaults, and uncustomized copies can receive system updates. Custom agents do not have a source template and are owned entirely by the organization.

Some system-agent fields are protected. The implementation allows limited updates such as color or model assignment, but blocks changing the system agent's core name, display name, or description.

## How an agent runs

The same agent can be used in several runtime situations:

| Runtime | What changes |
|---------|--------------|
| Chat | The chat template receives the current user message |
| Task | The task template receives task, project, git, and routine context when available |
| Gate | The gate template receives previous output and should combine it with task acceptance criteria or step instructions |
| Heartbeat | The heartbeat template receives previous and next run timing |
| Council | A council can ask an agent to contribute as a member or leader |

The agent identity stays the same. The runtime decides which prompt template and context variables are rendered for the turn.

## Permissions and tools

An agent only sees the platform tools allowed by its scopes. For example, `projects:read` adds read-oriented project tools, while `projects:write` adds mutation tools. Scopes are validated against the same platform scope registry used for API keys and organization members.

Assignments add more surface area:

- **Abilities** become callable specialist tools.
- **Domains** become explicit modes a user can activate.
- **MCP servers** add external tools when the worker connects to those servers.

Keep those three ideas separate: scopes decide which Nenjo operations are allowed, abilities describe specialist behavior, and MCP servers provide external tool endpoints.

Context blocks and Library knowledge are also separate. Context blocks are reusable prompt guidance. Library knowledge is source material an agent should search and read before making source-backed claims.

## Designing agents

A useful agent usually has:

- A short identity that makes its job obvious
- A model assignment that fits the cost and reasoning needs
- A stable system prompt for role and boundaries
- A developer prompt for working style and project conventions
- Focused templates for chat, tasks, gates, and heartbeats
- The smallest set of scopes and MCP servers needed
- Abilities only for specialist work the agent should be able to call
- Domains only for explicit mode changes a user should choose
